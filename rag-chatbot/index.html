Can a Chatbot Find
the Right Answer from
a Knowledge Base?

A web-based ticketing assistant prototype that uses Retrieval- Augmented Generation to retrieve relevant information before generating an answer with Gemini.

01 The Problem

What if finding the right ticketing information was easier?

The project started from a practical problem: users could experience confusion when trying to understand service procedures and fill in ticketing request forms.

Instead of relying only on keyword-based searching, the prototype was designed to retrieve relevant information from a prepared knowledge base and use that context when generating an answer.

02 The Idea

Don't just generate an answer. Find the context first.

The prototype uses Retrieval-Augmented Generation (RAG) so that a user's question can be matched against information stored in a vector database before the final response is generated.

This approach separates the retrieval of relevant information from the generation of the natural-language response.

03 Architecture

Three layers, one conversation.

The system is structured into Presentation, Application, and Data layers. The web interface communicates with the backend through a REST API, while the backend manages the RAG pipeline, vector search, and communication with the language model.

PRESENTATION LAYER React + Tailwind CSS Chat interface · Category filter · Response display
REST API
APPLICATION LAYER FastAPI · Python RAG pipeline · Embedding · Retrieval · Response formatting
Vector Search
DATA LAYER Qdrant Vector embeddings + document metadata
EXTERNAL AI Sentence Transformer + Gemini Embedding generation + answer generation
04 RAG Pipeline

From a question to a contextual answer.

When a user submits a question, the backend first converts the query into a vector representation. The vector is then compared with the stored embeddings in Qdrant to retrieve relevant documents.

01
Query Embedding

Sentence Transformer converts the question into a 384-dimensional vector.

02
Vector Search

Qdrant searches for the most relevant documents using cosine similarity.

03
Context Retrieval

The top relevant documents are selected as context for the response.

04
Answer Generation

Gemini generates a natural-language answer based on the retrieved context.

05
Response Formatting

The backend returns the answer together with document source information to the frontend.

05 Knowledge Base

The chatbot is only as useful as its knowledge.

The knowledge base was prepared from 20 source documents related to infrastructure ticketing. During indexing, the documents were divided into text chunks and converted into vector embeddings for semantic retrieval.

Source Documents 20
Vector Embeddings 187
Embedding Dimension 384

The embeddings were generated using paraphrase-multilingual-MiniLM-L12-v2 and stored in Qdrant together with document metadata.

06 User Experience

The answer matters. So does how users find it.

The frontend was developed with React and Tailwind CSS. The interface was designed around a simple conversation flow: users select a category if needed, type a question, and read the generated response together with its source information.

07 Testing

Does it actually work when people use it?

The prototype was evaluated through functional testing, Human Evaluation, answer comparison against ground truth, and usability testing.

Human Evaluation 4.26 / 5 Average score from 5 respondents
Ground Truth 60% Answer agreement with reference data
Usability 4.80 / 5 Average score from 10 respondents
08 What Worked

Retrieval helped keep the answers grounded.

Black-box testing showed that the main system functions worked as expected, including question submission, category filtering, context retrieval, response generation, and error handling.

The retrieval process allowed the chatbot to use relevant information from the knowledge base before generating a response, while the interface also displayed the sources used by the system.

09 Limitations

A RAG system is still limited by its knowledge.

Some questions were not fully covered by the available knowledge base. In those cases, the system could only return a fallback response rather than provide a complete answer.

The Human Evaluation also showed that while the language was generally clear, some answers could still lack detail. This pointed to the importance of improving the source documents and retrieval process rather than relying only on the language model.

Next improvement Expand the knowledge base and improve document indexing before moving toward direct operational integration.
10 What I Learned

Building an AI application is more than calling an API.

This project gave me hands-on exposure to connecting a web interface, backend API, vector database, embedding model, and LLM into one application flow.

It also taught me that the quality of an AI application depends on the whole pipeline: the source data, indexing, retrieval, prompt context, backend logic, and the way users interact with the final system.
